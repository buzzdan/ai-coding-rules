# Plan — Phase 1.5: extract a language-neutral core from the Go plugin

**Status:** proposed · **Scope:** `go-linter-driven-development/` only · **Output change:** none

This is the preparatory refactoring before adding a second language (Python). It applies
the plugin's own doctrine to itself: *make the change easy, then make the easy change*.
No rule, skill, agent, or command changes meaning. The shipped plugin directory stays
**byte-identical** to `main` at the branch point, except one CHANGELOG entry.

## Why this shape

The plugin already separates knowledge (rules, maxims) from workers (payload-fed
agents). What is still entangled is *inside each file*: portable prose (Principle, Why,
Design guidance, Fix pattern, the composition ladder, the Comment Value Toolbox) is
interleaved with Go-only material (canonical Go examples, `grep --include='*.go'`
detection commands, golangci linter names, `go test`, `//nolint`, `pkg_test`).

Measured coupling in the current plugin:

| Coupling point | Count |
|---|---|
| Fully qualified `go-linter-driven-development:` skill references | 34 |
| `*.go` / `_test.go` glob or suffix references | 99 |
| `golangci` references | 14 |
| Markdown files containing Go code fences | 28 of 49 |

A fork copies all of that (the TS/React plugin is the existing example of a fork that
then drifted). One bilingual plugin doubles every hunter's payload with the wrong
language's examples. So: one **core**, one **binding per language**, and a generator
that compiles them into the plugin directory the marketplace already serves.

## Non-goals (explicitly out of scope for 1.5)

- Any Python content. The Python binding is Phase 2.
- Changing any generated byte other than the CHANGELOG entry. In particular:
  - Not unifying the two routing tables (`skills/refactoring/SKILL.md` and
    `agents/lint-fixer.md`). They differ textually today; unifying changes output.
    Tracked as the first item of the Phase 2 backlog.
  - Not adding a "generated file" banner to outputs (changes bytes). CI and a root
    `CLAUDE.md` guard the outputs instead.
- Touching `ts-react-linter-driven-development/`.
- Removing inline Go idioms from core prose (`nil`, `ctx`, `goroutine`,
  `ParseX(raw) (X, error)`). They stay, get *inventoried* (see Residue), and are
  resolved in Phase 2 when the second language shows which ones need slots.

## Invariant that every commit must hold

```
go run ./tools/ldd-gen -check
```

renders every binding to a temp dir and diffs it against the committed plugin
directory; non-zero exit on any difference. The committed
`go-linter-driven-development/` **is** the characterization test — the refactor cannot
drift silently. CI runs the same command on every PR.

## Templating mechanism

Go `text/template`, default `{{ }}` delimiters (verified: no source file contains
`{{` or `}}` today). Exactly two constructs, nothing else:

| Construct | Meaning |
|---|---|
| `{{.Plugin}}`, `{{.Lang}}`, `{{.CmdPrefix}}`, `{{.SrcGlob}}`, `{{.TestGlob}}`, `{{.ProjectMarker}}`, `{{.Nolint}}`, `{{.CommentPrefix}}`, `{{.DefaultTest}}`, `{{.DefaultLint}}`, `{{.DefaultLintFix}}` | scalar from `lang/<lang>/profile.yaml` |
| `{{include "rules/R1/canonical-example.md"}}` | body of that file under `lang/<lang>/`, with exactly one trailing newline trimmed |

Plus two file-level rules, resolved by the generator without template syntax:

- **Whole-file override**: if `lang/<lang>/overrides/<core-relative-path>` exists, it
  replaces the core file entirely. Unused by the Go binding in 1.5; it is the escape
  hatch Phase 2 needs for rules whose *text* differs per language (R6 mock-vs-interface,
  R10 goroutines-vs-asyncio tasks).
- **Filename templating**: `core/commands/ldd-analyze.md` renders to
  `commands/{{.CmdPrefix}}-analyze.md` → `go-ldd-analyze.md`. `wire-repo-brain.md` has
  no prefix and renders as-is.

Include-file convention: no leading or trailing blank lines inside the include file;
the surrounding template owns the blank lines. This is what makes byte-identity
achievable without whitespace fights.

## The generator — `tools/ldd-gen`

Small Go program, its own module. Three commands:

| Command | Does |
|---|---|
| `ldd-gen -lang go` | render `core/` + `lang/go/` → `go-linter-driven-development/` (delete-then-write so removed sources remove outputs) |
| `ldd-gen -check` | render every binding under `lang/` to a temp dir; `diff -r` against committed dirs; exit 1 on any difference; print the unified diff |
| `ldd-gen lint-core` | the Residue report (below); exits 1 only on the three *hard* tokens |

Design notes, in the plugin's own terms:

- Leaf types: `Profile` (parsed YAML, validated: every scalar non-empty), `Binding`
  (profile + include/override lookup with `os.DirFS`), `Renderer` (template funcs:
  `include`). Each unit-tested with literals from an `internal/testdata` mini-tree.
- One golden test: render the Go binding, compare to the committed directory. It is
  the same check CI runs, expressed as `go test` so `-check` and the test cannot
  disagree.
- Resolution order per output path: override → template → passthrough; a path claimed
  by two sources is an error, not a silent win.
- Byte discipline: write outputs with `\n` line endings exactly as read; never
  `strings.TrimSpace` a whole file; includes trim exactly one trailing newline.
- Lint-green under a default `golangci-lint` config — the tool lives in a repo about
  linter-driven development.

**Residue linter (`lint-core`).** Greps `core/` and reports, grouped by file:

- **Hard (fail):** `go-linter-driven-development:` literal, `golangci`, `*.go` /
  `_test.go` globs, `//nolint`. These have vars or slots by construction; a hit means a
  missed substitution.
- **Soft (report):** `\bnil\b`, `goroutine`, `\bctx\b`, `context\.`, `sync\.`,
  `pkg_test`, `func `, `struct`, `interface`, `init()`, `wantErr`, `httptest`,
  `` ```go `` fences. This list *is* the Phase 2 backlog; it lands in `core/README.md`
  under "Residue" and is regenerated, not hand-maintained.
- Whitelist: attributed quotes in `maxims.md` (lines matching `— Rob Pike`).

## Acceptance criteria — 1.5 is done when all hold

- [ ] `make check` passes locally and in CI; `git diff main -- go-linter-driven-development/`
      shows only the CHANGELOG entry.
- [ ] Every file under `go-linter-driven-development/` is produced by the generator
      (`-check` fails on an unexpected extra file, so this is enforced, not audited).
- [ ] `lint-core` reports zero hard hits in `core/`.
- [ ] The Residue list is committed and is the generator's output, not hand-written.
- [ ] `go test ./tools/...` green; `golangci-lint run` green in `tools/ldd-gen`.
- [ ] `/plugin marketplace add ./ai-coding-rules` + install from the branch works
      exactly as before (manual smoke test; nothing about the served directory moved).
- [ ] `plugin.json` version unchanged at 2.9.1.

## Risks and how the plan absorbs them

| Risk | Mitigation |
|---|---|
| Whitespace fights at include boundaries break byte-identity | the include convention (no outer blank lines; trim one trailing newline) plus `-check` printing the diff — every mismatch is visible and local |
| Seams cut under the identity constraint are not the seams Python wants | whole-file override exists; Residue records known-suspect seams (documentation reference, testing philosophy Go idioms) |
| Someone edits the generated directory | CI check fails the PR; root `CLAUDE.md` tells Claude sessions where to edit |
| Adding Go tooling to a markdown repo raises the contribution bar | `Makefile` wraps everything in three verbs; the generator has no dependencies beyond the standard library and a YAML parser |
| Repo-root `go.mod` would make the plugin's own package-size hook fire on this repo | the module lives in `tools/ldd-gen/`; root stays module-free |
| Two routing tables tempt an "obvious" unification mid-refactor | explicitly deferred; first item on the Phase 2 backlog |

## Phase 2 backlog seeded by this plan

   version bump).
2. Split `skills/documentation/reference.md` at the Toolbox / Godoc seam.
3. Resolve the soft Residue list: which inline Go idioms in core prose need slots, which
   are fine as illustrative asides.
4. Add a generated-file banner to outputs once a content change is landing anyway.
5. Decide whether `ts-react-linter-driven-development` moves onto the core.

## Open decisions (not blocking; defaults stated)

- **YAML vs TOML for `profile`**: default YAML (`gopkg.in/yaml.v3`), matching
  `marketplace.json`'s spirit of plain config. Zero-dependency alternative is a flat
  `KEY=value` file parsed by hand.
- **Generator name**: `ldd-gen`. Alternatives: `pluginc`, `ldd-compile`.
- **Where the Residue list lives**: `core/README.md` (default) vs a separate
  `core/RESIDUE.md` regenerated by `make lint-core`.
